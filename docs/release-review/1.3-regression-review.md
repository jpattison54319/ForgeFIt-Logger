# Release 1.3 Regression Review (vs 1.2)

_Reviewed 2026-08-28 · `release/1.2` (`d939dc3`, build 91) → `release/1.3` (`9470236`, build 92)_

## Verdict

**Regression probability: low for the shipped surface area, with three items to
confirm before submission.** The single largest structural risk this codebase
carries — a CloudKit schema migration, which is one-way in production — is
**not present in 1.3**. The SwiftData schema is byte-identical to 1.2. The two
new features (App Intents/Siri and the render-performance rework) are built
behind explicit contracts and are backed by 140 new tests aimed at the exact
failure modes the changes introduce.

**What this review is not:** no Swift toolchain exists in the review
environment, so **nothing here was compiled or executed**. Every claim below is
either a reproducible static/diff fact, a Python gate this review actually ran,
or a code-reading judgement — labelled as such. The build/test/device evidence
that the release's own standard requires is listed under
[Evidence gaps](#evidence-gaps) and must be produced separately.

## 4. Feature review: App Intents / Siri / Spotlight

### 4.1 No forked start path

Intents never start a workout themselves. They construct a validated
`ForgeFitIntentDestination` (identifiers only), which becomes an in-process
deep link routed by `ContentView`, which calls the same `WorkoutFactory.start*`
entry points as the in-app buttons. This preserves the *"coaching preview ==
start"* class of invariant by construction: there is no second start
implementation that can drift.

Malformed input from the system fails closed — pinned by
`malformedWorkoutChoiceIdentifiersFailClosed` and
`malformedIntentDeepLinksFailClosed`.

### 4.2 Privacy-policy claims verified against code

`docs/privacy-policy.md` and `ForgeFit/Settings/PrivacyPolicyView.swift` were
changed together with identical prose and the same date — **the mirror
invariant holds**. Each new claim was checked against the implementation:

| Claim | Verification |
|---|---|
| "A catalog item contains its name, category, icon name, and a stable identifier. It never contains workout history, Health data, notes, or exercise targets." | `WorkoutChoiceRecord` has exactly four `String` fields. Type-level guarantee — the struct **cannot express** health data. All subtitles are static category labels ("Saved routine", "Cardio", "Saved yoga flow"). |
| "up to five matching routine names" | `Array(matches.prefix(5).map(\.record.title))` |
| "A later start lookup replaces the previous one" | Single defaults key; `save` overwrites |
| "Active-workout commands are not stored there" | `WorkoutIntentDiagnosticSnapshot` has no field capable of holding set values |
| "Settings → Reset all app data also removes it" | `AccountResetService` gained `await WorkoutIntentDiagnosticStore.shared.clear()` **and** `WorkoutChoiceCatalogStore.clear()` in this release |

Spotlight's `attributeSet` carries only title, the static category description,
and spoken-name aliases.

### 4.3 The write path is guarded

Siri can now mutate an active workout — the riskiest new capability in the
release. The tests target it adversarially:

- `testIntentNeverSilentlyReplacesAnActiveWorkout` (UI)
- `staleSetAnswerCannotOverwriteAConcurrentEditOrAdvanceAnotherSet`
- `hiddenEffortCannotBeWrittenThroughTheSiriBoundary`
- `updateAndReopenStayBoundToTheOriginallyResolvedSet`
- `finishConfirmationBecomesInvalidWhenAnySetValueChanges`
- `finishSavesSessionExertionWithoutChangingTheReusableRoutine`

Intent-driven set edits also roll back `workout.totalVolume` on failure.

### 4.4 Watch wire change is additive

One new `WatchCommand` case (`startNextTrackedWorkout`) plus one new payload
key, with a round-trip test added. Additive enum cases are safe in the
phone→watch direction here because the command travels watch→phone over the
immediate-reply channel and is never queued, so a mid-update version skew
degrades to a no-op rather than a delayed surprise start.

## 5. Performance work review

### 5.1 The approach matches the project's own standard

`docs/ios-performance-standard.md` (new in 1.3) requires that expensive
projections be computed once per *semantic data revision* with cache keys that
cover every field read. The implementation follows it:

- `RenderPerformanceRevision` routes SwiftData save notifications to the
  smallest affected render domain; CloudKit remote changes (which carry no
  entity identifiers) conservatively invalidate everything.
- `HomePerformanceRevision` keys include the fields an entity-only feed would
  miss — `activeMicrocycle` / `activeMesocycle` strings (so microcycle changes
  invalidate even though microcycle models are not in the routing table), row
  counts (insert/delete races), and the local day.
- Resident-but-hidden tabs reuse `cachedValue` instead of recomputing, and
  revision delivery is gated so the reveal picks up what changed while hidden.

The standard's four required cache proofs all have corresponding tests,
including the specific traps it names:

- "Memo computes once until a semantic input changes"
- "Editing an older completed workout invalidates suggestions" *(the
  count-plus-newest-timestamp trap)*
- "A non-newest exercise rename invalidates the O(1) name lookup"
- "CloudKit changes conservatively invalidate every render domain"
- "A hidden remote change settles before reveal exposes its revision"
- "Value-only modality projection matches the established award engine"
  *(incremental vs. full-scan parity)*

### 5.2 Live volume is now deferred to Finish — traced, and safe

`LiveWorkoutMetrics` changed from "recompute `workout.totalVolume` on every set
edit" to incremental per-set contributions held in an `@Observable`, writing the
parent aggregate **only when `workout.endedAt != nil`**. This is the change most
likely to cause a silent data regression, so the consumers were traced:

- `WorkoutFinisher.swift:653` calls `workout.recomputeTotalVolume()` on the
  terminal path, so the persisted aggregate is always correct for finished
  workouts.
- No live surface reads `workout.totalVolume` during a session — the logger
  summary, history feed, analytics, and `PersonalRecords` all sum `set.totalVolume`;
  `WatchLink` publishes no volume at all.
- Structural mutations (add/delete/reorder) fall back to a full `rebuild`.

Residual: the incremental deltas clamp with `max(0, …)`, which would mask drift
rather than surface it if a future call site mutates sets without going through
`refresh`/`rebuild`.

### 5.3 Launch work moved off the main actor, correctly shaped

`ImportedExerciseBackfill`, `SetTypeRetirementBackfill`, `WeightModeBackfill`,
and `ExerciseSeedRepository` each gained a cooperative variant following one
consistent, careful pattern: private `ModelContext`, `autosaveEnabled = false`,
`Task.checkCancellation()` between units, `rollback()` on error, re-check the
live row before applying stale off-main results, and **write the completion
stamp only after a durable save**, so a failed pass retries instead of being
permanently suppressed. The seeding logic itself was extracted verbatim into a
`nonisolated` function — behaviour-preserving by construction.

Note: the previous main-actor variants remain in the source but no longer have
production call sites (only tests). Dead code, drift risk over time, not a 1.3
regression.

## 6. Data migrations

### `RoutineLegacyBlockMigration` (new)

Converts legacy conditioning/yoga routine representations into first-class
blocks, deleting the superseded exercise rows. Runs on `onAppear` of the routine
editor, once per screen entry, then saves. Blast radius is bounded to routines
the user actually opens.

Test coverage is unusually complete for a destructive migration: a modern
routine is a **mutation-free** no-op (asserts `!context.hasChanges` *and*
unchanged timestamps), only the movement rows are removed, ordering is
normalized contiguously, the pass is idempotent after commit, and the result is
re-read **from a fresh `ModelContext`** to prove durability.

By design, a legacy yoga row without flow JSON becomes a yoga block with
`planJSON == nil` (pinned by test). Confirm that is the intended presentation.

### `WeightModeBackfill.convertIfNeeded`

Re-stamps pre-`WorkoutFactory` sets with their exercise's weight mode and moves
the stored value into the mode's field, then recomputes workout volume. This is
a repair of genuinely wrong historical tonnage — but it **changes numbers the
user has already seen**. See risk R2.

### R1 in detail — the one finding worth a decision before submission

`routinePrefers` changed from ranking on parent-row fields only
(`deletedAt`, `updatedAt`, `createdAt`) to ranking on
`authoredGraphUpdatedAt(routine)` — the max `updatedAt` across the routine's
**child** `exercises` and `blocks`.

The change is well-motivated and well-tested. It fixes a real bug (a folder move
bumps the parent clock, so the old ranking could pick a stale graph and
cascade-delete the user's edited exercises), and the new tests cover both
directions: `testNewerSoftDeleteWinsOverStaleLiveGraph`,
`testNewerAuthoredGraphBeatsOldTombstone`,
`testAuthoredGraphSurvivesLaterFolderMoveAndKeepsMovedPlacement`, plus
order-independence. `canonicalRoutines` is adopted consistently across all 18
routine-reading surfaces, so the UI and the maintenance pass agree.

The residual concern is **cross-device convergence**, which the file's own
doc comment asserts: *"All ranking inputs are CloudKit-synced, so devices
converge on the same survivor."* That was strictly true in 1.2, where every
ranking input lived on the same CloudKit record as the row being ranked. It is
weaker in 1.3: child rows sync as separate records and arrive incrementally, so
two devices running plan maintenance during a partial-sync window can compute
different `authoredGraphUpdatedAt` values for the same logical routine, pick
different survivors, and each hard-delete the other's choice.

The preconditions are narrow — duplicate rows exist only from the pre-split
CloudKit re-merge path, and two devices must run maintenance concurrently
mid-sync — but the operation is a hard delete with a cascade.

**Suggested action (not a blocker):** confirm on a two-device account with
duplicates that concurrent maintenance converges, or gate the collapse on a
quiescent-sync signal. At minimum, soften the doc comment so a future reader is
not assured of a property that now depends on sync timing.

## Evidence gaps

State these plainly to whoever signs off; they are not opinions about the code.

1. **Nothing was built or executed.** No Swift toolchain in this environment.
   `make test`, `make test-app`, `make build-ios`, and `make build-watch` are
   all **unrun** for 1.3. Compilation of ~11k new production lines is unverified.
2. **No CI.** The repository has no `.github/workflows`, so there is no
   automated build or test record for `release/1.3` to point at.
3. **No committed evidence artifact for 1.3.** Release 1.2 shipped a full
   `docs/release-audit-remediation/` story set plus `.xcresult` bundles under
   `artifacts/`. 1.3 adds a performance standard and a phased plan, but no
   corresponding acceptance or audit record.
4. **The performance claim is unproven by this review.** 1.3's own
   `docs/ios-performance-standard.md` requires Instruments evidence
   (Animation Hitches, SwiftUI, Time Profiler, Allocations, SwiftData) from a
   Release build on a ProMotion iPhone, and explicitly says: *"Never use a
   simulator pass, successful build/install/launch, average FPS, or subjective
   scrolling alone as proof of hitch-free physical-device frame pacing."*
   Source inspection can show the structurally unsafe work was removed. It
   cannot show the frame budget is met.

## Summary

1.3 is a large release (135 files, +11k production lines) that nonetheless
carries **less structural risk than its size suggests**, because it changes no
persisted schema, no backup format, and no unit handling. The new Siri surface
is contract-bounded and cannot express health data; its privacy claims were
verified line-by-line against the implementation. The performance rework follows
a written standard and is backed by tests that target the specific staleness
traps that standard names. The project's own acceptance gates pass and show
improved coverage.

The honest caveat: this is a **static** review. Confidence in the code's shape
is high; confidence that it builds, passes, and hits its frame budget rests
entirely on the checklist above, none of which could be executed here.
