# Watch delivery hardening — build 99

This follows the report of repeated historical workout launches after installing TestFlight 98 and roughly 30 seconds between a visible Watch heart rate and the phone reading. The earlier recovery changes did not cover every delivery path. The report alone cannot establish the original initiating failure or which binaries were installed on both devices.

## Changes

Watch Home and Siri now share an acknowledged start protocol. A start has a unique request ID and an eight-second lifetime, with a second expiry check immediately before persistence. It uses only `sendMessage`. The request ID becomes the persisted workout ID, so a repeated request finds the same active, finished, or discarded workout even after a phone process restart. An expired or failed start cannot remain in the shared save retry coordinator. Existing active workouts take precedence.

Both the generic phone command handler and the queued-message delegate reject the old start commands. Watch activation cancels previously queued starts while preserving logged set edits and Health save receipts. Phone terminal notices use the current committed snapshot plus an immediate notification; obsolete queued terminal notices are canceled while reset notices are preserved. A delayed HealthKit wake-up is a request to verify current state. It preserves an already verified recorder and its live stream. An unsolicited snapshot introducing an unseen workout also requires a correlated reply before it can start a recorder. It cannot create a new provisional recorder, and a verified idle response dismisses it without starting a workout. Recovery of an already running HealthKit session still preserves it until identity is verified.

The metrics coalescer retains one latest packet and one cancellable timer. The first valid heart rate is immediate, even if an energy packet was just sent. New samples, including an unchanged numeric heart rate, use a one-second interval. Other metrics use five seconds. A callback inside the interval schedules a trailing flush instead of dropping the final reading. Flush-time freshness checks prevent a sample that expired while waiting from becoming live again. Session reset cancels pending delivery.

Metrics are wired when WatchStore is initialized. Verification, recovered session binding, activation, and reconnection can flush the current reading through the same workout-identity and local-stop guards. Packets carry a stream identity, increasing sequence, and send timestamp. The phone rejects duplicates, older packets, partial headers, expired delivery, and wrong workout identity before updating live metrics or cardio consumers. Immediate and application-context delivery share this ordering gate. The fallback retains only the latest packet and has no real-time delivery guarantee from watchOS.

Start progress and failure are visible on Watch Home, with duplicate starts disabled and a Retry Sync control. Feedback replaces the readiness row during the request so it does not push the start button offscreen. Successful start haptics require a confirmed start. Both the request and the wait for the workout graph are bounded; a missing reply or snapshot leaves a visible recovery action.

The existing build 99 recovery controls, local Stop/Resume persistence, finish ownership, and custom reps/lb/kg quick increments are preserved. There is no data schema change, new health export, TestFlight upload, or release publication in this work.

## Evidence limits

The deterministic Watch fixture renders the production views and start/recovery coordinator but substitutes phone replies and does not start HealthKit. Package and simulator results do not establish physical sensor cadence, wrist-down WatchConnectivity latency, or paired finish propagation. The first recorded physical failure remains unconfirmed. Both devices need the updated code; matching version labels alone do not prove identical source or installation channel.

Physical ProMotion frame pacing and Instruments traces have not been established by these tests. An existing process-death gap during unresolved HealthKit save ownership also remains: guessing that Health saving failed after a timeout can duplicate a successful save. This work preserves truthful pending-save behavior instead of making that guess.
